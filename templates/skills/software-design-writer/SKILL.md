# Software Design Writer

Publish the SDD only as a Feature issue artifact; do not write a local feature file or cache. Explain how the feature works internally with enough local context for Scrum and implementation workers, not exhaustive coding checklists or duplicated system architecture.

For planned feature work, read the published BRD and required UX issue artifacts through GitHub MCP, not unpublished drafts or local substitutes. Find the intended Feature issue in the project's GitHub repository before creating one; use its confirmed issue identity and link as the stable parent/index. After the existing discovery, verification-proposal confirmation, final check-in, and Mermaid validation, publish the completed SDD through GitHub MCP as the SDD issue artifact on that Feature issue. Read back the same issue and artifact to confirm its identity and link before announcing success or allowing downstream use. On an uncertain write, read back before retrying; never create a duplicate Feature issue or claim an unpublished in-session draft is durable. If confirmation fails, state only confirmed effects and stop. After confirmation, show the Feature issue and SDD artifact links and name GitHub Epic/Story planning as the optional next stage; the user chooses whether to begin it. If that downstream GitHub workflow is unavailable, stop without local Epic or Story substitutes or a claim that hierarchy work was done.

At planned-stage entry, read only the published BRD and, for UI-changing features, published UX from the intended Feature issue through GitHub MCP into session context once per need. The SAD and other project-wide foundations remain repo-local. Missing, unpublished, or conflicting required content blocks SDD work: name the artifact and next GitHub check; do not substitute a local feature file or create an on-disk feature-artifact cache. Before publishing, identify repository, Feature issue, and SDD artifact. A call response alone is not confirmation: read back exact issue and SDD content, identity, and link. After timeout or uncertain update, reconcile a confirmed effect without duplicate retry; retry only if readback establishes absence. If readback is unavailable or conflicting, distinguish confirmed facts from uncertain effects, name SDD publication as blocked and the next check or access repair, and stop downstream work. Do not log private artifact bodies, credentials, raw prompts, or large payloads.

For planned-work terminal feedback, follow the project AGENTS.md terminal contract and binding UX mockups at compact and wide widths. After confirmed SDD readback, show `SDD published`, `Feature: <name>`, `SDD: <artifact link>`, then `Next: GitHub Epic and Story planning` as an optional user-selected stage. If SDD publication remains unconfirmed, show `SDD was not confirmed on GitHub`, `The Feature artifact could not be verified. Next work is paused.`, then `Check GitHub access, then retry.` Do not present an unconfirmed draft as published.

## Prerequisites and ownership

Read `docs/architecture.md`, selected architecture guidance, relevant repository context, and the authoritative published BRD and required UX Feature issue artifacts. Read applicable clean-code and implementation skills without duplicating them. A missing BRD routes to `business-requirements-writer`; `docs/architecture.md` missing or insufficient routes to `software-architecture-writer`; missing required UX routes to `ux-expert`. Explain the missing input and stop rather than use old-file fallback.

Before interviewing or writing, identify and read the workflow's selected architecture skill. Missing, unavailable, or ambiguous guidance requires workflow repair: run `sibu sync`. Do not choose, infer, or substitute a style. Conflicting guidance requires clarification. Selected guidance and SAD boundaries are binding.

UI mockups in UX are binding goals for structure, hierarchy, content, interactions and breakpoint layouts, not redesign targets. Surface feasibility conflicts for UX revision.

If the feature needs changed module boundaries or system-wide architecture decisions, pause SDD work and give a focused request for `software-architecture-writer`. Do not edit the SAD or invent new modules. Resume only after corrected SAD context and a user request to continue. Local algorithms and interface details that fit existing boundaries stay within SDD scope; do not force unnecessary SAD rework. Do not modify upstream artifacts, Scrum artifacts, implementation plans, or production code.

## Feature design content

Use proportionate sections for inputs and requirement coverage, summary, selected SAD modules and boundaries, responsibilities/interfaces, main execution flow, relevant data/state changes, failure behavior, important security/concurrency concerns, quality strategy and concrete verification, and risks/tradeoffs. Omit irrelevant detail. Separate planned verification from commands actually run. Keep exhaustive class/method inventories and story implementation checklists out.

Carry source BRD requirement IDs and qualify references with the Feature issue and BRD artifact identity; verify IDs resolve to its entries. Surface missing, invalid, or conflicting references instead of inventing IDs. Map relevant IDs to design decisions and applicable verification, naming deliberately unverified outcomes without requiring a standalone matrix. Require sufficient BRD context, not approval fields, signatures or sign-off.

Name relevant existing SAD modules and include sufficient promises/interfaces, ownership/exclusions, hidden complexity, and dependencies for downstream workers without copying the entire SAD. Apply selected architecture to concrete feature boundaries and ordering. If context is insufficient or contradictory, clarify upstream rather than guessing.

## Quality strategy

Choose only verification methods that add value for this feature. For each chosen method (for example, unit test, integration test, isolated live-agent eval, or human QA), state the concrete activity, relevant scenario or surface, who performs it, when it runs, what observable evidence it produces, and what would count as pass or failure. Distinguish automated checks from human judgment and say explicitly when human QA is required or excluded. Explain material skips rather than listing methods as placeholders. Identify validation commands where known without claiming they ran. Keep planned verification intent distinct from observed results; deterministic tests do not prove live agent behavior.

Separate **outcome verification** from **delivery evidence**. This section chooses methods for claims about feature behavior, not every Task's executable completion check. A Task may objectively show that an agreed file, template, configuration, or other deliverable was produced and passed its ordinary repository check without adding an excluded behavior test or claiming the behavior was proven. State what such evidence does and does not establish. Excluding a live eval, contract review, or human QA does not forbid a Task from proving that it delivered its assigned artifact; it does forbid treating that delivery check as equivalent to the excluded method. Leave exact Task checks to the implementation plan within these boundaries.

Write the settled verification approach as an easy-to-find SDD quality strategy, tied to relevant source BRD requirement IDs. Make every chosen method actionable enough that a planner can tell whether to create a unit test, run an integration check, arrange a separate live-agent eval, or wait for human QA. State meaningful exclusions and constraints without turning the section into an approval record or a universal test-method checklist.

## Visual explanation

Every SDD embeds at least one explanatory Mermaid diagram. For an interaction-driven feature, use a main-flow sequence diagram for the happy-path scenario showing the trigger, relevant participants, interactions/data, and response. Keep one scenario per Mermaid diagram: give each meaningful failure or edge case that needs visual explanation its own titled diagram, rather than packing alternative outcomes into the main flow or one omnibus diagram. Describe simple variants in prose instead of diagramming every possibility. For a change with no meaningful interaction flow, include one focused structural flowchart, state or data diagram and explain why a sequence would misrepresent the change. The exception changes diagram type, not the obligation: no completed SDD is diagram-free. Supplement only when useful and never invent unsupported behavior to populate a diagram.

## Discovery and user control

Read the required sources first, then interview one focused question at a time about remaining material decisions. Reuse settled answers; do not mechanically repeat questions answered by the user or sources. Ask meaningful follow-ups to partial answers and resolve material uncertainty instead of inventing decisions. There is no question-count limit or shortcut for complex work. Small changes need proportionate discovery, not filler questions.

During that interview, inspect the planned feature, its BRD and intended downstream work, and the relevant downstream skills for **known applicable feature-specific human gates**. Ask only about gates that apply to this feature, one focused question at a time; name the choice and consequence. Do not use a universal questionnaire. If eval authoring is not planned, do not ask Evaluation Targets or eval coverage questions. If no feature-specific gates apply, state that explicitly in the SDD's **Feature Decisions** section.

When eval authoring is planned, apply `eval-authoring`'s distinct gates before SDD finalization: first ask the engineer to confirm the Evaluation Targets and intended scope; then propose the target-specific Eval Coverage Plan and ask for explicit approval of scenarios and risk categories, grading choices, simulated tool behavior where applicable, and known gaps or exclusions. Targets alone do not approve coverage. Do not create eval suites, runners, fixtures, or other eval artifacts during SDD authoring.

Write one easy-to-find **Feature Decisions** section in the SDD. For each applicable approved decision, record a stable local ID, governing downstream skill and gate, exact human-approved choice, scope, and explicit human confirmation in self-contained words. Record eval target confirmation and eval coverage approval as distinct decisions, including their respective approved details. An unanswered question, inferred choice, mere SDD existence, or generic “SDD approved” statement is not approval. If a required answer is missing or ambiguous, including missing eval coverage details, give the engineer the specific unanswered question and pause SDD finalization until it is resolved; do not leave empty approval fields. The section is not an SDD-wide sign-off and grants no Git, model-route, credential, external-mutation, destructive-action, code-change, sync-ownership, or final Epic-review permission. Preserve those operational and final human gates.

Before writing the SDD, present the engineer with a concise, feature-specific outcome-verification proposal in plain language. For each proposed method, say what will actually be done, who will do it, when, over which scenarios or surfaces, and what pass/fail evidence it should produce. Identify any human QA as a concrete activity and say whether it gates delivery; if none is planned, say so. Distinguish ordinary Task delivery checks from these methods so an excluded method is not silently reintroduced downstream. Do not present bare method names or invent exact commands when unknown. Ask the engineer to confirm or correct this direction; incorporate corrections and restate a changed approach for confirmation before writing. Resolve material gaps with focused follow-ups before making the proposal.

For UI-changing features, derive named screens, states, and breakpoints from the binding UX mockups. Explain how a person will compare visual fidelity against those mockups, separately from functional tests and automated accessibility checks; automation does not prove subjective visual quality. For non-UI features, omit visual-review boilerplate.

Before writing, perform a final conversational check-in: “I am clear on my end. Is there anything else to cover before I write?” Incorporate corrections and wait for the response. This closes discovery, not a document sign-off ceremony. Do not add approval fields, signatures, or approval statuses. Never automatically execute the next stage; the user chooses progression. Preserve code-change permissions, story-level review, sync ownership choices, and external mutation authorization.

The verification proposal and its confirmation are distinct from that final check-in; the check-in cannot substitute for them. If the final check-in changes verification direction, restate and reconfirm the changed approach before writing. Do not add routine Story, Task, or Milestone approval pauses when downstream work stays within the settled approach.

## Embedded Mermaid validation

Inspect locally available parser/render capabilities without installing dependencies, fetching packages, or uploading private diagrams externally without permission. Check the exact final Mermaid blocks with an available parser or renderer. Correct reported failures and recheck after edits. Record the tool/version when obtainable and actual outcome in the document. Parsing proves syntax acceptance, not rendering; claim rendering only when it ran. Known unresolved parse/render errors remain blockers: report the specific failure, never relabel it a manual pass or claim success.

When tooling is unavailable, inspect syntax and relationships manually and state “manual-only; parser/render validation unavailable.” Writing with this limitation is allowed. Separately review semantic accuracy: actors, ordering, module boundaries, responses, and meaningful failure paths. Prefer conservative syntax, simple IDs, declared participants, balanced fences/quotes/blocks, single-line quoted labels, explicit subgraph spacing, and quoted punctuation-bearing edge labels. Avoid semicolons in sequence messages, raw multiline labels, and unsupported version-specific syntax.

Report the confirmed Feature and SDD artifact links and actual validation limits, or the blocked action and next step if publication remains uncertain. Keep diagrams and validation notes embedded, not in a separate companion.
