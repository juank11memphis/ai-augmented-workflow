# Agent-Guided Evals

Use this shared workflow when a developer asks to work on, run, troubleshoot, or fix existing Sibu evals in Codex or Claude Code. Eval authoring is separate; do not create or rewrite suites merely to make a failing run pass. The coding agent's own model is not the Model Under Evaluation (MUE) or Judge Model.

## Choose and run the selected scope

1. From the project root run `sibu evals suites`. Use its JSON `suites[].id` and `testCases[].id` to show choices; do not inspect suite JSON independently. Ask for one suite and scope: one case or all cases.
2. Run `sibu evals describe <suite>` for all cases, or `sibu evals describe <suite> --case <case_id>` for one. Show compatible `models`, `judgeModels`, `rubricRequired`, and saved choices. A missing or unavailable required tested/Judge suite default blocks the run: explain the affected role and require the developer to explicitly save a compatible choice before retrying. Old suites without defaults remain valid but still need required choices saved before execution. Do not silently use the coding agent's own model as either choice.
3. Run `sibu evals run <suite>` for all cases, without `--case` or run-wide model flags; saved defaults and case overrides resolve automatically. For one case, run `sibu evals run <suite> --case <case_id>` with saved choices, or add temporary `--model <model_id>` and `--judge <model_id>` only when applicable. One-case temporary choices never persist or become full-suite overrides. Wait for terminal JSON. Record the original scope, `runId`, `status`, `outcome`, `cases[].caseId`, and `attempts[].number`/`outcome`. A nonzero exit may carry useful blocked or failed JSON; inspect status rather than treating exit code alone as an assertion failure.
4. For a completed failing run, select only the first unresolved failed assertion in stable suite/case/check order from `failedAssertionIds` with `locatorStatus: available`; do not diagnose later failures yet. Keep its source run ID and `(caseId, attempt number, assertionId)` together. The selected result CLI currently accepts attempt **1** only: if a needed locator is absent, `unavailable`, `truncated` without a suitable ID, or points to another attempt, stop and explain that bounded evidence is unavailable. Do not infer IDs from suite JSON or load bulk artifacts. Run `sibu evals result <suite> <run_id> --case <case_id> --assertion <assertion_id>` and use only its bounded `failure` and `summary`. Pair `--case` and `--assertion`. An unselected `sibu evals result <suite> <run_id>` may supply bounded locators, not guessed IDs.

## Diagnose and propose

Keep one active failed assertion. State the observed run ID and case/attempt/assertion, what the bounded actual/expected/diagnostics show, the likely cause, uncertainty, and concise possible fixes. A failed assertion is distinct from blocked/error/interrupted/partial runs, missing credentials, unavailable runner or judge, invalid configuration, and missing/corrupt/unsafe artifacts. For those states, report the known reason and next user action; do not invent a prompt diagnosis or claim a pass. If the expectation or cause is ambiguous, ask a focused question before proposing an edit.

For one concrete fix, name the exact project-root paths, intended changes, rationale, and expected effect on the active assertion. Wait for explicit developer approval of that fix and those paths. A decline or changed scope stops without edits. Approval is conversational guidance plus native host permissions, **not** a Sibu-enforced authorization guarantee. Never edit secrets or credentials, even if suggested; ask the developer to handle access separately. There is no Sibu CLI mutation shortcut.

## Apply once and verify

Before editing, capture the working-tree baseline including pre-existing changes in and around approved paths. Preserve them. Only after approval, use the coding host's normal edit tools and permissions within the project root, limited to the named fix. Compare the post-edit changed-file list and delta with that baseline and approved scope; report actual changed files and delta, including pre-existing edits left untouched. If any change is unexpected, concurrent, or indistinguishable from your edit, stop before rerunning and request human review. Do not reset, overwrite, or silently absorb it.

After a safely scoped edit, automatically run the affected case **once** with saved effective choices or the originally selected one-case temporary choices, without another routine approval prompt. Record the fresh run ID and verify the active assertion using that run's complete attempt locators and bounded result where available. Advance only if the fresh completed result demonstrates that assertion passing. If it still fails, reanalyze its fresh bounded evidence and wait for another approved, scoped fix before any second edit. Report other failed or incomplete checks without diagnosing them yet. A blocked, partial, interrupted, error, unavailable, or uncertain rerun is not a pass: report the reason and next action, then stop. Do not rerun repeatedly to fish for a pass.

## Continue a full suite sequentially

After the active assertion passes, consider the next unresolved failure from the originally selected suite in stable suite/case/check order. Before proposing its fix, if its evidence predates an intervening edit, run that case once with saved effective choices and select its current failed assertion from fresh bounded locators; if the old failure disappeared, report that rather than repairing stale evidence. Keep only one active assertion. Each new fix needs its own explicit approval and scoped edit. Stop honestly on ambiguous evidence, unsafe changes, or non-convergence rather than silently changing failures or cycling indefinitely.

When all known failures are resolved, rerun the full suite exactly as originally scoped, without `--case` or run-wide model flags, using saved defaults and case overrides. Claim suite success only from this terminal run's actual completed, passing outcome—not from an edit, a focused pass, stale evidence, or a nonterminal run. If it fails, re-enter the same one-at-a-time loop using that run's bounded locators; if blocked or incomplete, report the known reason and next action without a success claim. For an originally selected single case, retain the focused outcome and do not add a full-suite rerun.
