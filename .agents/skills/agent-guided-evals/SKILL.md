# Agent-Guided Evals

Use this shared workflow when a developer asks to work on, run, troubleshoot, or fix existing Sibu evals in Codex or Claude Code. Eval authoring is separate; do not create or rewrite suites merely to make a failing run pass. The coding agent's own model is not the Model Under Evaluation (MUE) or Judge Model.

## Choose and run the selected scope

1. From the project root run `sibu evals suites`. Use its JSON `suites[].id` and `testCases[].id` to show choices. Ask for one suite and scope: one case or all cases. For a saved run, use its recorded suite, case, and attempt identities rather than current suite defaults.
2. Run `sibu evals describe <suite>` for all cases, or `sibu evals describe <suite> --case <case_id>` for one. Show compatible `models`, `judgeModels`, `rubricRequired`, saved suite defaults, and selected-case effective/source choices. A missing or unavailable required tested/Judge suite default blocks the run even if a case overrides it: explain the affected role and require the developer to explicitly save a compatible choice before retrying. Old suites without defaults remain valid but still need required choices saved before execution. Do not silently use the coding agent's own model as either choice. To set or change one case's tested or Judge override, use `sibu evals choice <suite> --case <case_id> --role <tested|judge> --token <choiceToken> --set <model_id>`; to reset just that role to inheritance, use `--reset` instead of `--set`. Get a fresh token from describe before each save. Never change the other role or suite default implicitly.
3. With authorization for any paid run, run `sibu evals run <suite>` for all cases, without `--case` or run-wide model flags; saved defaults and independent case overrides resolve automatically in suite order. For example, suite tested default X with one of nine cases overridden to Y runs eight on X and one on Y; Judge overrides resolve separately on rubric cases. An unavailable case override blocks before any paid call: tell the developer to **Replace** it with a compatible model or **Inherit** with `evals choice --case <case_id> --reset`; re-describe for a fresh token and require an explicit new run. Never silently fall back, skip, or automatically retry paid calls. For one case, run `sibu evals run <suite> --case <case_id>` with saved choices, or add temporary `--model <model_id>` and `--judge <model_id>` only when applicable. One-case temporary choices never persist or become full-suite overrides. Wait for terminal JSON. Record the original scope, `runId`, `status`, `outcome`, `cases[].caseId`, actual per-case tested/Judge model, and `attempts[].number`/`outcome`; inspect saved evidence for completed, failed, partial, or incomplete attempts rather than today's defaults. A nonzero exit may carry useful blocked or failed JSON; inspect status rather than treating exit code alone as an assertion failure.
4. Select one active issue in stable suite/case/check order. For a completed failing attempt, prefer its first unresolved `failedAssertionIds` entry; keep `(runId, caseId, attempt number, assertionId)` together. For partial or incomplete attempts without failed assertions, select the first incomplete case/attempt and its execution issue. Do not diagnose later issues yet. Missing, truncated, unavailable, or non-assertion CLI locators do not make saved artifacts off limits.

## Inspect the selected saved run

Use `sibu evals result <suite> <run_id>` and a selected result when useful, but **not as the only evidence source**. The result CLI's assertion-based `--field` read is not required to diagnose an incomplete attempt. Locate the selected run under the project root at `evals/artifacts/<suite>/<run_id>/run.json`; read its `cases/<case_id>/<attempt>.json` for output, assertions, diagnostics, failure provenance, response references, and gaps. Read only the specific source records or raw response files referenced by that attempt when needed. For example, an incomplete `approximate-price` attempt may have no failed assertion but a `target-2` record in `providerResponses.records`; follow that record's `locator` to the saved response `.bin` and compare it with the attempt's diagnostics. Never substitute normalized `output` for an absent raw response.

Before any direct read, validate the selected run/case/attempt identity against saved metadata. Resolve each path beneath the selected run's `evals/artifacts` tree; reject traversal, symlinks, unexpected file types, or a locator pointing outside that run. If Sibu reports an unsafe, tracked, corrupt, or otherwise blocked artifact, stop rather than bypassing that safety decision. Start with the smallest relevant file or excerpt; read a **full selected artifact** when excerpts cannot establish the cause. Do not bulk-load unrelated runs or cases. Do not paste large bodies, secrets, personal data, or raw response text into chat, diagnostics, or logs; report only concise, redacted findings and file identities.

## Diagnose and propose

Keep one active issue. State the observed run ID and case/attempt (and assertion, if present), what the selected output/response/diagnostics show, the likely cause, uncertainty, and concise possible fixes. Distinguish a failed assertion from blocked/error/interrupted/partial runs, missing credentials, unavailable runner or judge, invalid configuration, and missing/corrupt/unsafe artifacts. Diagnose an incomplete attempt from saved evidence when possible; otherwise report the known gap and next user action. Do not invent a prompt diagnosis or claim a pass. If the expectation or cause is ambiguous, ask a focused question before proposing an edit.

For one concrete fix, name the exact project-root paths, intended changes, rationale, and expected effect on the active issue. Wait for explicit developer approval of that fix and those paths. A decline or changed scope stops without edits. Approval is conversational guidance plus native host permissions, **not** a Sibu-enforced authorization guarantee. Never edit secrets or credentials, even if suggested; ask the developer to handle access separately. There is no Sibu CLI mutation shortcut.

## Apply once and verify

Before editing, capture the working-tree baseline including pre-existing changes in and around approved paths. Preserve them. Only after approval, use the coding host's normal edit tools and permissions within the project root, limited to the named fix. Compare the post-edit changed-file list and delta with that baseline and approved scope; report actual changed files and delta, including pre-existing edits left untouched. If any change is unexpected, concurrent, or indistinguishable from your edit, stop before rerunning and request human review. Do not reset, overwrite, or silently absorb it.

After a safely scoped edit, request explicit authorization before any paid rerun; editing approval alone does not authorize one. If authorized, run the affected case **once** with saved effective choices or the originally selected one-case temporary choices. Record the fresh run ID and verify the active issue using that run's saved artifacts and bounded result where useful. Advance only if the fresh completed result demonstrates the active assertion passing or the incomplete execution issue resolved. If it remains, reanalyze fresh evidence and wait for another approved, scoped fix before any second edit. Report other failed or incomplete checks without diagnosing them yet. A blocked, partial, interrupted, error, unavailable, or uncertain rerun is not a pass: report the reason and next action, then stop. Do not rerun repeatedly to fish for a pass.

## Continue a full suite sequentially

After the active issue resolves, consider the next unresolved failure or incomplete attempt from the originally selected suite in stable suite/case/check order. Before proposing its fix, if its evidence predates an intervening edit, ask authorization for a paid refresh, then run that case once with saved effective choices and select its current issue from fresh saved evidence; if the old failure disappeared, report that rather than repairing stale evidence. Keep only one active issue. Each new fix needs its own explicit approval and scoped edit. Stop honestly on ambiguous evidence, unsafe changes, or non-convergence rather than silently changing failures or cycling indefinitely.

When all known issues are resolved, request explicit authorization before a paid full-suite rerun. If authorized, rerun the full suite exactly as originally scoped, without `--case` or run-wide model flags, using saved defaults and case overrides. Claim suite success only from this terminal run's actual completed, passing outcome—not from an edit, a focused pass, stale evidence, or a nonterminal run. If it fails, re-enter the same one-at-a-time loop using that run's saved evidence; if blocked or incomplete, report the known reason and next action without a success claim. For an originally selected single case, retain the focused outcome and do not add a full-suite rerun.
